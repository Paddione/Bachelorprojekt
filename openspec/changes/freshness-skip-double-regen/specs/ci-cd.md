## ADDED Requirements

### Requirement: Rebase-Pfad skippt Regen-Zyklus bei offenem oder laufendem Freshness-Regen

The rebase-healing paths (`scripts/pr-refresh.sh`, `scripts/devflow-ci-watch.sh` DIRTY
preflight, `scripts/factory/babysit-prs.sh` freshness-class fix) SHALL consult a shared
detector (`scripts/freshness-regen-in-flight.sh`) before their own regenerate-commit-push
cycle. The detector SHALL report "in flight" when either an open pull request with a head
branch named `chore/freshness-regen-*` exists OR a run of `.github/workflows/freshness-regen.yml`
is in status `in_progress` or `queued`. When the detector reports in flight, the path SHALL
skip its own regeneration commit (the open or running cycle heals main) but SHALL still
complete its rebase and push. When nothing is in flight, the paths SHALL behave unchanged.
The detector SHALL be offline-testable via an injectable `gh` command, mirroring the
`PR_REFRESH_GH_CMD` indirection.

#### Scenario: pr-refresh skippt Regen-Commit bei offenem Regen-PR *(BATS)*

- **GIVEN** ein gestubbtes `gh` meldet einen offenen PR mit `headRefName: chore/freshness-regen-123`
- **WHEN** `pr-refresh.sh <N>` auf einem CONFLICTING-PR läuft und den Rebase abgeschlossen hat
- **THEN** führt der Lauf KEINEN eigenen Regen-Commit-Push aus (`task freshness:regenerate`-Folgecommit bleibt aus)
- **AND** die Bilanz meldet den PR als übersprungen-bezüglich-Regen, nicht als geheilt-per-Regen

#### Scenario: pr-refresh verhält sich unverändert ohne laufenden Regen *(BATS)*

- **GIVEN** ein gestubbtes `gh` meldet weder einen offenen `chore/freshness-regen-*`-PR noch einen aktiven Run
- **WHEN** `pr-refresh.sh <N>` einen CONFLICTING-PR heilt
- **THEN** läuft der bestehende Pfad (Rebase → Regeneration → Commit → Push) unverändert weiter

#### Scenario: devflow-ci-watch DIRTY-Preflight respektiert den Detektor *(BATS)*

- **GIVEN** der Detektor meldet „in flight"
- **WHEN** das DIRTY-Preflight von `devflow-ci-watch.sh` den Rebase abgeschlossen hat
- **THEN** wird kein zusätzlicher „chore(ci): regenerate freshness artifacts after auto-rebase"-Commit erzeugt

#### Scenario: babysit-prs freshness-Fix greift nicht bei offenem Regen-PR *(BATS)*

- **GIVEN** der Detektor meldet „in flight" und ein roter PR ist class=freshness
- **WHEN** `babysit-prs.sh` seinen Fix-Pfad erreicht
- **THEN** wird kein `chore: refresh (ci-babysitter)`-Commit auf dem PR-Branch gepusht und der Lauf endet ohne Fehler

## MODIFIED Requirements

### Requirement: Generierte Artefakte sind Konflikt-Magnete — Auflösung via git checkout --ours

The system SHALL resolve merge conflicts on auto-regenerated artifacts (`docs/generated/**`,
`docs/code-quality/repo-index.json`, `k3d/docs-content-built/architecture/index.html`) by
running `git checkout --ours <file>` for each conflicting file during rebase, because these
files are regenerated by `freshness-regen.yml` after every main push and the PR-branch version
is always stale relative to main.

The `merge=ours` attribute SHALL be understood as a **local-only** resolution. GitHub does not
execute custom merge drivers server-side, so the same artifacts that resolve silently during a
local rebase still surface as a conflicting merge state on the PR. A locally clean merge tree
therefore does NOT disprove a conflict reported by GitHub, and the two observations MUST NOT be
treated as contradictory evidence.

The resolution direction SHALL be documented as **rebase-asymmetric**: during `git rebase`
„ours" is the NEW BASE (origin/main), so the driver silently discards the branch-side changes
to these artifacts; only a merge of main INTO the branch resolves in favor of the PR branch.
Every automated or manual rebase of a branch touching these artifacts MUST therefore be
followed by `task freshness:regenerate` against the rebased tree — this post-rebase
regeneration is the compensation, not the driver itself.

#### Scenario: Freshness-Regen erzeugt Rebase-Konflikt auf generiertem Artefakt

- **GIVEN** ein PR committed `docs/generated/graph.json` neu und `freshness-regen.yml` hat nach dem letzten main-Push dieselbe Datei automatisch neu committet
- **WHEN** der Entwickler `git rebase origin/main` auf dem PR-Branch ausführt
- **THEN** entsteht ein Merge-Konflikt in `docs/generated/graph.json`
- **AND** die korrekte Auflösung ist `git checkout --ours docs/generated/graph.json && git add docs/generated/graph.json` — nicht manuelles Mergen

#### Scenario: merge=ours-Driver löst beim Rebase zugunsten des neuen Bases auf — Rebase-Falle

- **GIVEN** `git config merge.ours.driver true` ist gesetzt und der PR-Branch trägt eigene Änderungen an einem `merge=ours`-Artefakt
- **WHEN** `git rebase origin/main` auf dem Branch läuft und in dem Artefakt konfligiert
- **THEN** behält der Driver die Version des NEUEN BASES (origin/main) und verwirft stillschweigend die Branch-seitige Änderung — „ours" zeigt beim Rebase aufs Base, nicht auf den PR-Branch
- **AND** die Branch-seitige Artefakt-Aenderung existiert nur wieder, wenn NACH dem Rebase `task freshness:regenerate` gegen den neuen Baum läuft

#### Scenario: Derselbe Driver wirkt auf GitHub nicht — Phantom-Konflikt

- **GIVEN** ein PR berührt eines der 21 in `.gitattributes` mit `merge=ours` markierten Artefakte,
  und dasselbe Artefakt wurde auf `main` ebenfalls regeneriert
- **WHEN** `git merge origin/main` lokal ohne Konflikt durchläuft, `gh pr view <N> --json mergeStateStatus`
  aber `DIRTY` oder `CONFLICTING` meldet
- **THEN** ist das kein Widerspruch und kein Fehler in `.gitattributes`: GitHub führt serverseitig
  keine Custom-Merge-Driver aus und sieht einen gewöhnlichen Inhaltskonflikt
- **AND** die Auflösung ist, den Branch auf `main` nachzuziehen und die Artefakte danach mit
  `task freshness:regenerate` gegen den neuen Stand neu zu erzeugen

#### Scenario: Rebase-Richtung ist in .gitattributes und Taskfile dokumentiert *(BATS, source verification)*

- **GIVEN** `.gitattributes` und die `freshness:regenerate`-NOTE in `Taskfile.yml`
- **WHEN** ein Entwickler vor einem Rebase die Konvention nachliest
- **THEN** findet er in beiden Dateien die Rebase-Asymmetrie („ours" = neues Base beim Rebase) und die Pflicht der Post-Rebase-Regeneration dokumentiert
