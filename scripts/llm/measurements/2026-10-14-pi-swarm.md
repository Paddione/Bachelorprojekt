# pi-Schwarm auf dem Quasar-Worker (:8123): 10–12 Agenten gleichzeitig — Messplan

Stand: 2026-10-14, **vorbereitet, noch nicht gemessen** (braucht den
GPU-Host).

## Frage

Haelt der Quasar-Worker 10–12 gleichzeitig arbeitende pi-Agenten aus, und was
kostet das den einzelnen Agenten? Grundlage:

- Durchsatz-Messung (`2026-10-14-quasar-vllm-6-streams.md`): 678 tok/s bei 6
  synthetischen Stroemen, noch keine Saettigung.
- Harness-Vergleich (`2026-10-14-harness-ctx.md`): pi-L0 startet mit 1.839
  Token und kommt bei der Fixture-Aufgabe auf 5–7k Spitze — 12 Agenten
  brauchen damit grob 60–90k vom KV-Pool (216.078 Token).

## Randbedingung: max-num-seqs

`serve-worker-vllm.service` laeuft mit `--max-num-seqs 10`. Bei 11–12 Agenten
warten also 1–2 Anfragen, solange 10 laufen — das misst der Lauf mit
(`waiting max`). Fuer 12 echte parallele Agenten den Server vorher umstellen:

```bash
systemctl --user cat serve-worker-vllm | grep -n -- '--max-num-seqs'
sed -i 's/--max-num-seqs 10/--max-num-seqs 12/' ~/.config/systemd/user/serve-worker-vllm.service
systemctl --user daemon-reload && systemctl --user restart serve-worker-vllm
until curl -sf http://127.0.0.1:8123/v1/models >/dev/null; do sleep 5; done
journalctl --user -u serve-worker-vllm --since "5 min ago" --no-pager | grep -E "KV cache size|Maximum concurrency" | tail -1
```

Sinnvolle Reihenfolge: erst 10 mit dem heutigen Server (Baseline, keine
Warteschlange erwartet), dann 12 einmal mit `max-num-seqs 10` (Warteschlange
sichtbar) und einmal mit 12.

## Aufbau

`scripts/llm/pi-swarm.sh` startet N pi-Agenten gleichzeitig auf die
Fixture-Aufgabe aus dem Harness-Vergleich:

- je Agent eigener detachter Worktree, eigener Proxy (`ctx-proxy.mjs`, eigener
  Port ab `--base-port`+1, eigene Sitzung via `setsid`, eigenes Log) und
  eigenes `PI_CODING_AGENT_DIR` — Anfragen sind eindeutig zuordenbar, und ein
  Agent, der per bash-Tool Prozesse beendet, reisst die anderen nicht mit;
- pi-Aufruf wie `pi-L0..L2` im Harness-Vergleich (`--level`);
- ein Poller schreibt jede Sekunde `num_requests_running`,
  `num_requests_waiting` und KV-Auslastung nach `metrics.tsv`;
- Differenzen von `generation_tokens_total`, `prompt_tokens_total` und
  `num_preemptions_total` ueber den ganzen Lauf.

Lokal gegen einen vLLM-Simulator geprueft (12 Agenten, max 10 gleichzeitig):
`running max 10, waiting max 2`, alle Proxys und Worktrees danach entfernt.

## Messbefehle

```bash
cd ~/Bachelorprojekt && git pull
curl -s http://127.0.0.1:8123/metrics | grep -E '^vllm:num_requests_(running|waiting)'   # beide 0
bash scripts/llm/pi-swarm.sh --n 10 --level L0 --out ~/harness-ctx-runs/swarm-10-L0
bash scripts/llm/pi-swarm.sh --n 12 --level L0 --out ~/harness-ctx-runs/swarm-12-L0-seqs10
# nach Umstellung auf --max-num-seqs 12:
bash scripts/llm/pi-swarm.sh --n 12 --level L0 --out ~/harness-ctx-runs/swarm-12-L0-seqs12
```

Ausgabe je Lauf (auch in `summary.json`):

```
12 Agenten (L0): <geloest>/12 geloest, <n> mit success-Zeile, Proxy verloren: <n>
Wanduhr <s> s, je Agent Median <s> s / max <s> s, <n> Anfragen
Kontext: Start-Median <tok> tok, Spitze <tok> tok
vLLM: <tok/s> tok/s erzeugt, running max <n>, waiting max <n>, KV max <0..1>, Preemptions <n>
```

Je Agent: `agents.jsonl`; Lastverlauf: `metrics.tsv`.

## Was zaehlt

- **Loesungsquote** im Schwarm gegen Einzellauf (pi-L0 einzeln: 2/2 im
  Harness-Vergleich) — leidet die Qualitaet unter Last nicht, ist der Track
  parallel nutzbar.
- **Agent-Dauer Median/Max** gegen Einzellauf (22–32 s) — der Preis der
  Parallelitaet je Agent.
- **running max = N** (bzw. = max-num-seqs), **Preemptions = 0**, **KV max**
  deutlich unter 1 — sonst begrenzt der Server, nicht der Harness.
- `proxy_lost > 0` heisst: ein Agent hat seinen eigenen Proxy beendet; dieser
  Agent zaehlt dann nicht.
